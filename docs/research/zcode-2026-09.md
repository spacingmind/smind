# ZCode research — lessons for smind (2026-09)

Research doc, not a plan. ZCode (Z.ai's coding workbench, v3.14.3,
Apache-2.0, `github.com/zai-org/ZCode`) cloned read-only at `refs/zcode`.
Findings below are grounded in files read directly in that checkout;
the privacy-incident section also uses external sources (Perplexity
search, cited) since the checkout's git history is squashed to 3 commits
and can't confirm pre-open-source behavior.

## Overview

ZCode is a much larger, more mature product than smind: an Electron
desktop app + web mode + CLI, built around a TypeScript monorepo
(`pnpm` workspaces) with a dedicated agent-runtime package
(`apps/zcode-cli/packages/core`) separate from the desktop/services
layer. It ships GLM/Zhipu as its first-party model but routes it through
the same generic protocol adapters as OpenAI/Anthropic providers. Its
standout features are a multi-subagent "dynamic workflow" DSL with live
concurrency retuning, a "Goal Mode" auto-continuation loop, and
remote-control via existing chat platforms (Telegram/WeChat/Feishu/
Discord/webhook) rather than a native mobile app. It was open-sourced
on 2026-09-20 in the wake of a real privacy incident: a "Repo Wiki"
codebase-indexing feature silently uploaded whole workspaces (including
`.git` history) to Alibaba Cloud OSS with no working opt-out. That
feature and any trace of it are absent from the current checkout.

## Architecture summary

**Routing / GLM wiring** — `packages/provider/src/resolver.ts:182-376`,
`config/provider-config.ts`, `config/provider-data-schema.ts`. No
failover/round-robin engine exists (grepped, none found). Instead: a
3-layer config resolver (builtin < personal < live account overlay),
provider `access` type is a discriminated union
(`api-key` | `zhipu-coding-plan-api-key` | `zhipu-account`), and GLM/Zhipu
providers get `group: "zai-family"|"bigmodel-family"` which
`resolveProviderOrder()` always sorts first. GLM speaks the *same* three
wire protocols (`anthropic-messages`/`openai-chat-completions`/
`openai-responses`) as everything else — no GLM-specific adapter code.
Quota (`services/src/usage-stats/providers/zcodeMcpQuotaProvider.ts`) is
display-only, not a routing input. A separate ticket-based "Off-Peak"
scheduler (`services/src/session/offPeakTaskService.ts`) polls a server
endpoint for cheaper-capacity scheduling — unrelated to client-side LB.

**Permission modes** — `packages/shared/src/execution-state.ts:4`
(`"build"|"edit"|"yolo"|"auto"` + separate `planEnabled: boolean`),
mapped to user labels "Ask before changes" / "Edit automatically" /
"Plan mode" / "Full access" in
`packages/ui/src/chat-input-toolbar/display-help.ts`. Single decision
function `PermissionService.checkPermission()`
(`apps/zcode-cli/packages/core/src/permission/service.ts:97-231`) returns
`allow|ask|deny`; tools flagged `alwaysAsk` are unconditionally
un-bypassable, even under `yolo`. `auto` mode exists in the type but is
literally unimplemented ("reserved but not implemented yet", line ~140).
The 3.14.x "approval dialog granting full access" is an auditable
event+receipt flow
(`apps/zcode-cli/packages/core/src/runtime/permission-full-access.ts`,
`contracts/src/interfaces/permission-full-access.ts`): grants are scoped
to the queue items pending at grant time and persisted as an idempotent
receipt, not a silent global toggle.

**Dynamic workflows** — ZCode's largest subsystem (100+ files across
`dynamic-workflow`, `dynamic-workflow-runtime`, `core/src/workflow`,
`contracts/src/workflow`). A workflow is a TypeScript script the model
writes (`CreateWorkflow` tool) against a fixed facade
(`agent()/.ask()`, `files.glob/grep/read`, `world.run()`, `phase()`,
`report()`, `artifact.*`); no nesting. Concurrency ceiling is
`max(1, min(16, os.availableParallelism() - 2))`
(`bootstrap/src/app/workflow-concurrency-ceiling.ts:1-43`). A process-
singleton governor (`workflow-concurrency-governor.ts`) buckets admission
by `${providerId}/${modelId}`, runs an AIMD controller per bucket that
reacts to live `model_request_completed`/`rate_limited`/
`provider_overloaded` events, and round-robins admission across runs
sharing a bucket so one run's fan-out can't starve another's. The
literal "dynamic" (3.14.x) feature is `AmendWorkflow({run_id,
max_concurrency})` detected as concurrency-only
(`core/src/tool/handlers/amend-workflow-retune.ts:33-41`) and applied as
a **live in-place mutation** — no stop/restart, no transcript loss.

**Goal Mode** — internally "Target" (`ZCodeSessionGoal`,
`apps/zcode-cli/packages/core/src/runtime/methods/target*.ts`). `/goal
<objective>` sets a session-scoped goal with budget stats (tokens, time,
context, tool calls, iterations). After each turn,
`runActiveTargetContinuationLoop()`
(`target-continuation-loop.ts:45-86`) calls a **separate verifier model
call** (`target-completion-verification.ts:41-89`) fed the whole
transcript; if not `passed`, it injects a model-only system reminder
with the verifier's `nextAction` and auto-resubmits. Toggleable
(`targetCompletionVerification.enabled`), and explicitly suppressed
under Plan mode.

**Remote/SSH/WSL workspaces** — `packages/server/src/remote/` (~40
files). One interface, `IRemoteBackend`
(`remote/backend.ts`: `detect/upload/exec/exists/readFile`), three
implementations (`ssh-backend.ts` via `ssh2`, `wsl-backend.ts` shelling
to `wsl.exe`, `docker-backend.ts`). A text-line JSON handshake
(`remote/handshake.ts`) tolerates SSH banner/MOTD noise before finding a
`zcode-hello` line.

**Mobile remote control** — no native mobile app or push notifications
exist. The remote-control surface is chat bots:
`packages/services/src/bots/botsService.ts` + providers for Telegram,
WeChat (`weixinProvider.ts`), Feishu/Lark, generic webhook
(`packages/shared/src/bots.ts`: `BotProvider` also lists `discord`,
`wecom`). Pairing via WeChat-style QR polling or a 30s bind code
(`BOT_BIND_CODE_TTL_MS`). `packages/ui/src/WebRemoteControlDialog.tsx`
configures a bot channel as a workspace's remote-control surface, with
per-bot `allowedWorkspaces`/`allowedCommands` and a `replyMode` verbosity
setting.

**Plugin/MCP/skills** — `packages/services/src/plugins/pluginsService.ts`
is a retired stub (`throwRetiredPluginManagement()` on every mutator);
real plugin execution moved into
`apps/zcode-cli/packages/adapters/src/plugins/` (marketplace, github/zip
sources). `pluginSyncService.ts` recognizes `.zcode-plugin/plugin.json`,
`.claude-plugin/plugin.json`, and `.codex-plugin/plugin.json`
interchangeably — deliberate interop with Claude Code's and Codex's
plugin formats. Skills are a separate first-class concept
(`services/src/skills/`, bundled skills under
`apps/zcode-cli/packages/bundled-skills/skills/`).

**Desktop + web mode auth** — `scripts/zcode-distribution/runner.mjs`:
`shouldProtectHost(host) = !isLocalHost(host)`; loopback bind → no token
by default, non-loopback (`--host 0.0.0.0`) → auto-generated token
(`randomBytes(24).toString("base64url")`), overridable via
`--token`/`--no-token`. Server (`packages/server/src/http.ts`) checks
`?token=` query param, upgrades to an `HttpOnly` cookie
(`zcode_lite_token`) on match; gates only `/ws*` and `/api/*`. A separate,
stricter `packages/zcode-server-cli` "server-core" is fail-closed: it
throws if asked to bind non-loopback at all, reflecting two trust tiers
(`desktop-continuous` vs `web-remote-replayable` in `http.ts`).

**Context usage display** —
`packages/ui/src/chat-input-toolbar/contextUsage.tsx` attributes context
budget to named buckets (`messages | system_prompt | meta_user_context |
skills | tool_prompt | system_tool_schemas | mcp_tool_schemas`) and
renders a stacked multi-segment progress bar with a per-bucket hover
breakdown, plus a compact `used/size (pct%)` summary.

**Architecture-policy enforcement** — `architecture-policy.yaml` (root)
declares per-module `managed: true/false`; only `storage` is fully
managed today (explicit incremental-migration comment). Enforcement
(`scripts/architecture/{index,policy,architecture-check}.mjs`) checks
file/contract line limits, `domain` layers forbidding Node IO imports,
one-way `layerOrder` dependency direction, `ui` module forbidding direct
`repo|runtime|service` imports, cross-module imports restricted to
declared `publicEntrypoints`, import cycles, and expired time-boxed
exceptions. A `.architecture-baseline.json` fingerprint file lets
pre-existing violations pass while failing new ones; `--changed` mode
scopes checks (plus reverse-dependency expansion) to a git diff, making
it fast enough for `pnpm verify:pre-push`.

Ordered roughly by leverage-per-effort: the top five (context meter,
permission carve-out, auditable full-access grant, loopback-token
default, architecture linter) are all small, self-contained, and don't
touch the wire protocol — good near-term picks. Goal Mode, remote
backends, and chat-bot control are the biggest wins but each needs an
ADR before implementation per AGENTS.md rule (d): they change the agent
loop, add a workspace source type, or add a new remote-control trust
boundary respectively.

## What to avoid

- **The privacy incident itself, as a design pattern.** External sources
  (Perplexity search, corroborating InfoWorld, The Register, SCMP, and
  others) describe a default-on "Codebase Indexing"/"Repo Wiki" feature
  that packaged whole workspaces — including `.git` history, LFS caches,
  and global app config — and uploaded encrypted archives straight to
  Alibaba Cloud OSS via a client-requested credential
  (`/api/v1/snapshot/upload-credential`), with **only the vendor holding
  the decryption key**, so users could not inspect or delete their own
  uploads. No working opt-out existed; Z.ai disabled the feature, wiped
  the bucket, and open-sourced the client on 2026-09-20/21. Notably, the
  feature and any trace of the upload path (`aliyun`/`ali-oss`/`wiki`/
  `embedding`/etc.) are **absent from the current open-sourced checkout**
  — the repo's git history is squashed to 3 commits, so this can't be
  independently re-derived from `refs/zcode`, only from the external
  reporting. Lesson for smind: any future codebase-indexing, context-
  caching, or "send this to a model for global search" feature must be
  opt-in by default, keep data local unless the user explicitly enables
  a remote path, and never hold the only decryption key server-side
  without also giving the user a way to audit/delete what was sent —
  a stronger, more concrete version of what smind's AGPL self-hosting
  stance (ADR-0003) already leans toward.
- **Half-implemented enum variants.** `auto` mode exists in ZCode's type
  system and is fully wired through the UI but does nothing
  (`"Auto mode is reserved but not implemented yet"`). AGENTS.md already
  forbids "half-finished implementations" — this is a concrete example
  of what that looks like when it ships anyway.
- **Retired code left in place as a throwing stub** rather than deleted
  (`pluginsService.ts`'s `throwRetiredPluginManagement()` on every
  method). If smind retires an internal path, delete it; don't leave a
  stub that just throws a "this used to work" error.
- **Unbounded orchestration complexity as a default.** The dynamic-
  workflow subsystem is 100+ files and its own SKILL.md is 1521 lines.
  If smind eventually adds multi-subagent orchestration, keep it scoped
  to the phase that actually needs it rather than building the general
  DSL up front — smind's phase-gated roadmap already leans this way.
- **Generic "Codex-clone" UI, per user complaints** (external context):
  reinforces, rather than adds to, what `docs/research/ui-ux-polish-2026.md`
  already found — that shadcn/Tailwind defaults read as generic without a
  deliberate visual thesis. No new action here beyond following that doc.

## Overlaps with the prior Paseo/UI-UX research

- `docs/research/ui-ux-polish-2026.md` already recommended permission
  prompts that state exact action/reversibility, stay anchored in the
  timeline, and offer scoped "always allow" rules with a preview. ZCode's
  `permission/` component family and its receipt-scoped full-access
  grant (not a silent global toggle) are a real-world instance of that
  same principle — validates the prior recommendation rather than
  surfacing a new gap.
- That same doc's mobile section researched actionable push (inline
  Approve/Reject, ~62% no-open-app rate) as the missing half of smind's
  mobile story; push notifications are confirmed still unbuilt (per the
  ROADMAP and this session's UI/mobile skim). ZCode sidesteps native
  push entirely by using existing chat platforms as the remote-control
  surface instead. Worth weighing as an alternative or interim step
  before investing in the E2EE-data-minimization design push
  notifications will need — but it's a different trust model and would
  need its own ADR, not a substitute for finishing the push design.
- `docs/research/dual-mode-ui.md`'s tab-kind/panel-manifest model and
  "attention rail" concept has no direct ZCode equivalent — ZCode's
  closest analogue (`phase()` markers drawing a workflow's node graph) is
  scoped to workflow visualization, not general pane management. No
  overlap to note beyond this.
- `docs/research/uiux-audit.md`'s design-token/dark-mode gaps are
  orthogonal to ZCode, which ships its own from-scratch `DESIGN.md`
  system — parallel prior art, not something smind is behind on because
  of ZCode specifically.
