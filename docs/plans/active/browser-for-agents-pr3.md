# Browser for agents, PR 3: the human-only enable flag and the allowlist (spec)

Governing ADR: `docs/decisions/0061-browser-for-agents.md` (Accepted; amendments of 2026-11-15 and 2026-11-16). Order of the lane: PR 1, 1b, 2 (merged or in review), **PR 3 (this spec)**, PR 3b (proxy authentication and the per-run socket, spec in `browser-for-agents-designs.md`), PR 4 (the daemon-side permission gate, which flips `browser.GateReady`), PR 5 (provider table). One PR at a time from a fresh `origin/wave/desktop`. High-risk (a new human-only surface, a store table, permissions): foreground two-sub-agent review, the Steward's own review, mutations.

## What PR 3 is, and what it is not

PR 3 stores, per workspace, the human's decision to switch the browser on and which exact hosts it may reach, and gives only a human a way to change it (an RPC, a CLI, both on the human-only tables). It also adds the daemon-wide kill switch and fills the navigation deny list.

**It does not open anything.** `browser.GateReady` stays `false` (PR 4 flips it, after PR 3b), so with the flag on and every host allowed, no run gets the `smind-browser` row and `browser.call` still refuses. A test pins this: enabling the flag changes nothing an agent can reach.

## Acceptance criteria

- **P3-AC1 Storage.** A new table `browser_settings` (in `schema.sql`, `CREATE TABLE IF NOT EXISTS`, so no column migration is needed): `workspace_id INTEGER PRIMARY KEY REFERENCES workspaces(id) ON DELETE CASCADE`, `enabled INTEGER NOT NULL DEFAULT 0`, `allow_hosts TEXT NOT NULL DEFAULT '[]'` (a JSON array of canonical hosts), `profile_mode TEXT NOT NULL DEFAULT 'ephemeral'`, `updated_at`, `updated_by TEXT NOT NULL DEFAULT ''`. No row means OFF with an empty allowlist. Store methods `GetBrowserSettings(workspaceID)` (a missing row is the zero value, never an error), `SaveBrowserSettings`, `DeleteBrowserSettings`; a deleted workspace takes its row with it.
- **P3-AC2 Validation on every write.** Each allowlist entry goes through `browser.NormalizeAllowHost` (an exact host or IP literal: no wildcard, scheme, port, path or userinfo; link-local, metadata, multicast and unspecified addresses refused), is stored canonical, deduplicated, at most 50 entries; an invalid entry refuses the whole write and names the entry. `profileMode` accepts only `ephemeral` in this PR (the column exists so the persistent mode, a separate human toggle in the ADR, needs no migration later); `persistent` is refused with "not available yet".
- **P3-AC3 The kill switch.** A daemon-wide config value `browser.disabled: true` (YAML) and the environment variable `SMIND_BROWSER_DISABLED=1`, read on every gate decision and every `browser.call` (no restart), that no RPC can change. While set: the workspace gate is false for every workspace, `browser.call` refuses with "the browser is disabled by the daemon's configuration", and open browser sessions are closed at the next call or sweep. The settings RPC reports `killSwitch: true` and still lets a human edit the stored values (they take effect when the switch is cleared).
- **P3-AC4 Human-only RPCs.** `browser.settings.get`, `browser.settings.set` and `browser.data.clear` are handlers that refuse a nil request context and any run-scoped caller (`refuseAgent`); their names are on `permpolicy.HumanOnlyRPCs`; none is on `RunScopedMethods`, in a plugin capability or in any MCP tool list; the `browser.` prefix stays on the plugin never-list. `browser.call` remains the one run-scoped `browser.` method and a test pins that exactly one `browser.*` method is run-scoped. `get` is human-only too (the allowlist is configuration, not an agent's business).
- **P3-AC5 Results.** `get` and `set` return `{workspaceId, enabled, allowHosts, profileMode, killSwitch, available, chromeInstalled, installStep, updatedAt, updatedBy}`: `available` is `browser.GateReady` (false in this release: the UI says the tools are not yet offered), `chromeInstalled`/`installStep` come from `DetectChrome` (never installing anything). `set` takes optional `enabled`, `allowHosts` (the full replacement list) and `profileMode`; absent fields are unchanged; it records `updated_by` from `inboxActor(rc)`, publishes `browser.settings.updated {workspaceId}` on the event bus and **closes the workspace's browser session** (`Manager.Close`) so the new policy applies at once. `data.clear` ends the workspace's session now and removes any profile directory of the workspace (with ephemeral profiles nothing persists, so this is "stop and forget").
- **P3-AC6 The gate and the policy inputs.** The registry's browser gate hook (`SetBrowserGate`) is installed by the server and answers `enabled && !killSwitch` from the store; `browserHost.allow` returns the stored allowlist; the **deny list** is filled from every address a page must never reach: the daemon's listen address, every other listener in the config (the web and gRPC-web listeners, the relay's local ports), every address of a fleet-linked daemon, and the desktop's proxy origin when the config names one (each parsed with the same host parser as URLs; a wildcard bind denies the port everywhere). Changing the allowlist closes the session (AC5), so a running browser never keeps an old policy.
- **P3-AC7 CLI.** `smind browser status|enable|disable|allow add <host>|allow rm <host>|clear` in `cmd/smind`. `enable`, `disable`, `allow` and `clear` are on the human-only command table (`humanOnlyCLI`, path `browser`, `status` stays read-only in the table's sense but its RPC is human-only, so it also refuses in an agent run); all refuse when `SMIND_RUN_ID` is set (the same guard as `smind permission`), the floor rule denies them in an agent's shell, and they take `--workspace <id>` (default: the workspace of the current directory, like the other task commands). Output names the stored state and, when the gate is dark, says so.
- **P3-AC8 Dark stays dark.** With the flag on, the allowlist set and `GateReady` false: no run's contract carries the browser row, `browser.call` refuses at the gate, and `status` shows `available: false`. With `GateReady` flipped in a test build, the row appears exactly when the flag is on, the kill switch is off and the run is an ordinary user run (the existing `row_present_only_when_all_gates_hold` test grows the store-backed case).
- **P3-AC9 Peers and relay.** The fleet host audit lists the browser methods as not callable by a peer daemon; relay-served sessions follow the saved-grants precedent (a paired device is a human surface and may call the three methods; the E2EE channel test lists them next to the grants methods).
- **P3-AC10 The stated limit.** The enable method is as human-only as the RPC principal is today (ADR-0056 is still Proposed: an unidentified local connection counts as the human). The floor rule and the CLI refusal cover the common routes. This is stated in the CLI help, the ADR amendment and the PR body, as saved grants did; the Settings UI text (a later web PR) states it next to the switch.

## Decisions taken unless told otherwise (none architectural)

- `persistent` profiles are not implemented in this PR (the ADR makes them a separate human toggle and the launcher has no persistent mode); the column exists, the value is refused.
- At most 50 allowlist entries per workspace; hosts are stored canonical, so `LOCALHOST.` and `localhost` are one entry (loopback names need no entry at all: loopback is always allowed).
- A name the human adds may only resolve to public addresses (ADR amendment of 2026-11-15); the CLI and the RPC say so in their refusal text for a private-looking name, and tell the human to add the IP literal instead.
- `browser.data.clear` is "end the session and remove the profile directories": the ADR's "clear browser data" for a world where only ephemeral profiles exist.

## Not in PR 3

The Settings UI (the plan's web PR B3), the provider table (PR 5), proxy authentication and the per-run socket (PR 3b), the permission gate (PR 4), a persistent profile, any wildcard allowlist.

## PR 3: progress, deviations and validation

Built as specified, with these deviations decided while building:

- **No `browser.settings.updated` event.** A new bus topic needs entries in the relay and channel allowlists and nothing consumes it until the Settings UI PR, so the topic arrives with its consumer. A change still closes the workspace's browser session at once.
- **The deny list is the daemon's own addresses**: the listen address and every `server.hostnames` entry on the same port (a wildcard bind denies the port everywhere, by the policy). The config names no other daemon listener (the relay and gRPC-web listeners are command-line flags of other commands), and a fleet-linked daemon's address is inside opaque link JSON and non-loopback anyway: it is unreachable unless the human allowlists it. The desktop proxy origin arrives with the desktop host (B4), which is the only thing that creates it.
- **`allow add`/`allow rm` are one atomic RPC** (`allowAdd`/`allowRemove` on `browser.settings.set`, applied under the daemon's lock, hosts matched by canonical form); the CLI does no read-modify-write, so two commands at once cannot drop a host. The daemon stays the only validator.
- **Deny list fails closed and keeps the loopback companions**: a listen address that is not loopback still denies that port on 127.0.0.1, localhost and ::1; an unreadable config is an error and the call is refused. Host names are capped at 253 characters and labels at 63.
- **Relay**: the three settings methods are wrapped so only a local (non-relay) connection reaches them, in addition to `refuseAgent`.
- **Kill switch environment parsing**: `SMIND_BROWSER_DISABLED` is ON unless it is an explicit 0/false/off/no/n/f; the environment never turns off a file's `disabled: true`; a config that cannot be read fails closed.
- **`--workspace` is required** on the CLI (no current-directory default): an explicit target for a security switch. Not done from P3-AC9: the fleet host audit has no entry (relay connections are refused by `browserLocalOnly`, which is stricter than the saved-grants precedent).
- **Stated limits (review findings, not fixed here)**: the kill switch closes a live session at the next `browser.call` or the idle close, not at once; a call racing a settings change can run once under the old settings; `data.clear` ends the session (ephemeral profiles go with it) and does not sweep profiles orphaned by a crash; `allow rm` cannot remove a stored entry that no longer passes validation (edit by replacing the list).
- **The `browser` CLI row is `bare`** on the human-only table, so a renamed binary or `go run` cannot slip past the floor.
- `browser.settings.get` and `.set` carry a fixed `note` (the rule for names: a host name must resolve to public addresses, an intranet host is added by IP literal).
