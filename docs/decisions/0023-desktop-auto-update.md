# 0023: Desktop auto-update with the Tauri 2 updater

## Status

Accepted (2026-10-11). The user approved the signing, endpoint, channel, UX
and daemon-interplay defaults below on 2026-10-11. Implementation plan:
`docs/plans/active/desktop-auto-update.md`. Builds on ADR-0013 (bundled UI,
scoped IPC bridge) and `docs/plans/active/desktop-macos-app.md` (M2 bundled
daemon, M4 CI, M5 update-when-idle).

## Context

The desktop app ships only as installers attached to a GitHub Release (macOS
`.dmg` per arch, Windows NSIS/MSI). To get a new version a user has to notice
the release, download it and reinstall by hand. Apple and Windows code signing
are out of scope for now (macOS is ad-hoc signed, Windows unsigned), so the
OS gives us no trust chain for an update either. The updater therefore needs
its own.

The macOS app bundles a matching daemon (`desktop-macos-app` M2). Updating
the app brings a newer bundled daemon; the M5 rule already decides when that
daemon is swapped in.

## Decision

1. **Mechanism: `tauri-plugin-updater` (Tauri 2), driven from Rust.** The
   shell checks, downloads and installs. The webview never supplies a URL, a
   version or a signature: it can only ask Rust to *check* and to *install the
   update Rust already found*.

2. **Signing: Tauri updater signatures (minisign), separate from OS code
   signing.**
   - The **public key** lives in `desktop/src-tauri/tauri.conf.json`
     (`plugins.updater.pubkey`). The plugin refuses an update whose
     signature doesn't verify against it; there is no "skip verification"
     setting and we never set `dangerousInsecureTransportProtocol` in the
     committed config.
   - The **private key** is generated locally with `tauri signer generate`,
     kept outside the repo (`~/.tauri/smind-updater.key`) and stored as the
     GitHub Actions secret `TAURI_SIGNING_PRIVATE_KEY`. It is never committed,
     logged or uploaded as an artifact. The key has no password, so
     `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` is not set (an unset secret is an
     empty string, which Tauri treats as "no password"); if a password is ever
     added, it goes in that secret.
   - Losing or rotating the key means installed apps can no longer verify new
     releases. Users would have to reinstall by hand once. This is accepted
     and documented in the README.
   - Apple notarization and Windows Authenticode stay out of scope.

3. **Endpoint and channel: one stable channel, a `latest.json` on each GitHub
   Release.**
   - `plugins.updater.endpoints` has exactly one entry:
     `https://github.com/spacingmind/smind/releases/latest/download/latest.json`.
     GitHub's `latest` alias resolves to the newest **non-draft, non-prerelease**
     release, and `release-please-config.json` sets `prerelease: false`, so a
     pre-release is never served. The client also refuses a pre-release
     version string (`version_comparator`), so the guarantee doesn't depend on
     one side.
   - There are no beta/nightly channels.
   - `latest.json` is generated by the release workflow's `publish` job from
     the artifacts the build jobs produced, and uploaded to the Release
     **last**, after every artifact it references, so a client never sees a
     manifest that points at a missing file.
   - Platforms: `darwin-aarch64` and `darwin-x86_64` (the `.app.tar.gz`, one
     per arch, renamed with the arch because Tauri names both
     `smind.app.tar.gz`), and `windows-x86_64` (the NSIS installer). Each
     entry carries the asset's download URL for that release tag and the
     contents of its `.sig`. Linux has no updater: the only Linux bundle is a
     `deb`, which can't self-update, so the menu item and the launch check are
     not built there.

4. **Updater artifacts are opt-in per build.** `bundle.createUpdaterArtifacts`
   is **not** in `tauri.conf.json`; it lives in
   `desktop/src-tauri/tauri.updater.conf.json`, merged with `tauri build
   --config` only when the signing key is present. Tauri fails a build that
   asks for updater artifacts without a private key, so putting it in the base
   config would break `task desktop:mac`, every PR build and every fork.
   - PR and manual builds have no secret, so they skip updater signing and
     still produce the installers.
   - A **real release** (`release_created == 'true'`) passes a
     `require-updater-signing` input, so a missing secret there fails the build
     loudly instead of publishing a release that silently can't be updated.
   - The secret is exposed only to the single `tauri build` step, not to the
     job's other steps or third-party actions.

5. **UX: ask first, never install silently.**
   - **When:** one check shortly after launch (background; a failure is
     logged only, since being offline at launch is normal), and on demand from
     a new menu item, **Check for Updates…** (macOS: in the `smind` app menu
     after About; Windows: in Help).
   - **Prompt:** when a newer version exists, the UI shows a dialog with the
     new version, the current version and the release notes, and two buttons:
     **Update & restart** and **Later**. Nothing is downloaded until the user
     confirms. The dialog closes with Later, Esc or the close button. "Later"
     doesn't nag again in the same session (the launch check runs once; a
     manual check always re-asks).
   - **Install:** after confirmation Rust downloads (progress shown in the
     dialog), verifies the signature, installs and restarts. On Windows the
     NSIS installer takes over and relaunches.
   - **Errors are non-blocking:** a manual check or an install failure shows a
     toast (no modal) with the reason; the app keeps running on the current
     version.
   - **Placement:** the prompt is a web-UI dialog (so it follows the app's
     light/dark theme and matches the daemon banner), not a native dialog. The
     menu item emits an event to the UI, like the existing `menu-action`
     events; the UI calls two new commands.
   - **IPC surface:** two new commands, `app_update_check` and
     `app_update_install`, added to `capabilities/proxy.json` and the
     `build.rs` manifest (the capability test pins the exact allowlist).
     The plugin's own JS-facing permissions (`updater:*`) are **not**
     granted. `app_update_install` takes no arguments: it installs the update
     held in Rust state by the last successful check.

6. **Daemon interplay: no second path.** After a macOS app update the new
   app starts, finds the older managed daemon (`comparison == "older"`), and
   the existing M5 flow applies: it is updated automatically only when no runs
   are in flight; otherwise the user is asked. The daemon process is detached
   and survives the app restart, so installing an app update never interrupts
   running agent work. The updater does not touch, stop or restart the daemon.
   On Windows (WSL2 daemon, downloaded from the release by the existing
   flow) nothing changes either.

7. **No backend or daemon changes.** The daemon binary, `/healthz` and the
   proxy are untouched.

## Alternatives considered

- **Native dialog (`tauri-plugin-dialog`) for the prompt.** Smaller, with no
  new IPC commands. Rejected: it can't show long release notes or progress,
  doesn't follow the in-app theme, and blocks the Rust thread while shown.
- **Silent background download, prompt only to restart.** Rejected by the
  user: never install silently, and ask before downloading.
- **Grant the plugin's JS API (`updater:default`) to the bundled UI.** Rejected:
  it widens the webview's authority (it can choose the endpoint or headers)
  for no benefit; two narrow commands do the job.
- **`latest.json` on a separate host or branch (e.g. GitHub Pages).** More
  moving parts. The Release already carries every artifact, and `latest`
  gives stable-only for free.
- **A universal macOS binary, or a single `darwin` entry.** The app is
  per-arch by design (`desktop-macos-app` decisions); per-arch manifest
  entries keep it that way.
- **`createUpdaterArtifacts` in the base config.** Breaks keyless builds (see
  decision 4).

## Consequences

- Releases need one repository secret before updates can be published; until
  it is set, the next real release build fails at the macOS/Windows build
  step (by design, decision 4).
- The first release carrying this feature has to be installed by hand; only
  later releases can be updated in place. A real end-to-end update can only be
  tested after two releases exist.
- An update changes the app's ad-hoc code signature on macOS. Notification
  permission and similar per-app OS grants may need re-confirming after an
  update. This was not measured.
- Another failure mode on the release path: if `latest.json` generation fails,
  the release has installers but no updates, and the `publish` job fails
  rather than succeeding quietly.
